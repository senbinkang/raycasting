# AI 解说音频预生成 — 方案

> 2026-07-14

## 目标

消除 MiMo API 实时调用的 2-8 秒延迟，让解说音频即时播放。同时去掉"用户手动上传语音样本"的步骤。

## 核心思路

1. **语音样本嵌入代码** — 于谦语音样本 base64 化，作为默认值硬编码在 JS 中，无需用户上传
2. **模板音频预生成** — 25 条固定模板文本，一次性调用 MiMo 生成克隆音频，base64 嵌入代码
3. **运行时零 API 调用**（模板事件） — 触发事件直接取缓存播放
4. **LLM 事件降级** — 动态文本仍需实时 MiMo，但失败时自动降级为浏览器 TTS

## 文件协议兼容方案

`file://` 协议下无法使用 `fetch()` 加载外部文件。唯一兼容两种协议的方式：**把所有音频数据以 base64 形式嵌入 JS 文件，通过 `<script>` 标签加载**。

代价是 JS 文件体积增大（估算见下文），但一次加载后浏览器缓存，后续刷新瞬时完成。

## 体积估算

| 内容 | WAV 大小 | Base64 大小 |
|------|---------|------------|
| 语音样本 | 663 KB | ~885 KB |
| 25 条模板音频（每条 ~2 秒 22kHz mono） | ~2.2 MB | ~2.9 MB |
| **合计** | **~2.9 MB** | **~3.8 MB** |

3.8 MB 的 JS 文件对游戏来说可接受。HTTP 部署时 gzip 可压到 ~2.5 MB。

## 运行时代码流程

### 初始化

```
页面加载
  → CommentaryVoiceSample.js 提供默认语音样本 base64
  → CommentaryAudioCache.js 提供预生成音频映射 { "文本": "base64音频" }
  → CommentaryService.init()
      → 检查 localStorage 是否有用户上传的语音样本
          → 有：覆盖默认值（并清空旧音频缓存，因为声音变了）
          → 无：使用默认值
      → 将音频缓存加载到内存 Map（不存 IndexedDB，已在 JS 文件中）
```

### 模板事件（useLLM: false）

```
事件触发 → 随机选模板文本 → 内存 Map 查找 → 找到 → Audio.play() 即时播放
  找不到（不应发生）→ 浏览器 TTS 兜底
```

### LLM 事件（useLLM: true）

```
事件触发 → LLM API 生成文本
  → 成功 → MiMo API 语音克隆
      → 成功 → 播放
      → 失败 → 浏览器 TTS
  → 失败 → 模板文本 → 预生成音频播放
```

## CommentaryService 改动要点

```
当前：
  _speakMimo(text) → 每次都调 MiMo API → 等 2-8s → 播放

改后：
  _speakMimo(text) → 直接调用（LLM 事件用）
  _speakTemplate(text) → 查内存缓存 → new Audio(base64).play()  // 新增
  _speakBrowser(text) → SpeechSynthesis（不变，作为降级方案）
  
  _doSpeak(text, eventType) → 根据 eventType 选策略：
      useLLM: false → _speakTemplate(text)  // 模板事件，零延迟
      useLLM: true  → _speakMimo(text)       // LLM 事件，实时克隆
                      失败 → _speakBrowser(text)
```

## generate_audio_cache.mjs 脚本

一次性 Node.js 脚本，仅在需要重新生成音频时运行：

1. 读取 `assets/yuqian_voice_sample.wav` → base64
2. 生成 `game/CommentaryVoiceSample.js`（导出语音样本常量）
3. 遍历 25 条模板文本，逐条调 MiMo API
4. 将返回的音频 base64 写入 `game/CommentaryAudioCache.js`
5. 打印进度

以后如果修改模板文本，重新运行此脚本即可。

