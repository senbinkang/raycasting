## 零、助理开新对话前必读（5 条硬规则）

> ⚠️ **这是本文件唯一必须读的部分，其余都是细则**。违反任何一条 = 流程错误。

| # | 规则 | 怎么做 |
|---|------|---------|
| R1 | **任何对话必须生成 md 文件留痕**，没有例外 | 完成后必须在 `doc/操作记录/` 或 `doc/_workflow/会话计划/` 生成 md |
| R2 | **任何对话必须先出大纲 → 等你批准 → 再动手** | 哪怕你说「帮我改个 bug」，也必须先用一段文字复述需求 + 列出改什么 + 问你是否 OK，批准后才写代码 |
| R3 | **回复末尾必须告知文件位置** | 格式固定：`已生成记录：doc/xxx/xxxxx.md` |
| R4 | **先读 `todoList.md`，再动手** | 了解当前项目进度，避免重复或冲突 |
| R5 | **不要主动删除任何 doc 下的 md 文件** | 文件多了用目录归类，不要删 |
| R6 | **完成功能后必须提醒提交 commit** | 操作记录生成后，基于改动内容生成 commit message 贴给你看，你批准 wording 和改动点都 OK 了才执行 `git commit` |

## 一、对话流程（三阶段，任何对话都走）

```
阶段一：出大纲（助理写 → 等你批准）
  └─ 在 doc/_workflow/会话计划/ 生成 YYYY-MM-DD-<主题>-大纲.md
  └─ 内容：理解复述 + 具体做什么 + 涉及文件 + 预估工作量
  └─ 你批准前，任何代码都不改

阶段二：出执行计划（你批准大纲后 → 再等你批准）
  └─ 在 doc/_workflow/会话计划/ 生成 YYYY-MM-DD-<主题>-执行计划.md
  └─ 内容：步骤编号 + 每步目标 + 具体操作
  └─ 你批准前，任何代码都不改

阶段三：执行 + 验证 + 记录 + 提醒 commit
  └─ 按执行计划操作
  └─ 浏览器/命令行验证
  └─ 在 doc/操作记录/ 生成 YYYY-MM-DD-<主题>.md（含改动清单 + 验证结果）
  └─ 基于改动生成 commit message → 贴给用户确认（模板见「四·五」）
  └─ 用户批准 commit message → 执行 `git add .` + `git commit -m "..."`
```

## 二、文件命名与存放规则

| 文件类型 | 存放目录 | 命名规则 | 示例 |
|----------|----------|----------|------|
| 大纲 | `doc/_workflow/会话计划/` | `YYYY-MM-DD-<中文主题>-大纲.md` | `2026-06-14-raycasting性能优化-大纲.md` |
| 执行计划 | `doc/_workflow/会话计划/` | `YYYY-MM-DD-<中文主题>-执行计划.md` | `2026-06-14-raycasting性能优化-执行计划.md` |
| 操作记录 | `doc/操作记录/` | `YYYY-MM-DD-<中文主题>.md` | `2026-06-14-raycasting性能优化.md` |
| 建议/诊断类（放在项目 doc 根） | `doc/` | `<项目>-<主题>-建议.md` 或 `<主题>_建议.md` | `raycasting_改进建议.md` |

> 规则：主题词用中文，不超过 10 个字；日期 YYYY-MM-DD；同主题多版本加 `-v2`/`-v3`，不要覆盖旧版本。

## 三、回复模板

### 模板 A：阶段一「大纲」回复

直接贴大纲 md 内容 + 文件链接，末尾加：**「你批准这个大纲我再进入阶段二写执行计划；有改动直接告诉我」**

### 模板 B：阶段二「执行计划」回复

直接贴执行计划 md 内容 + 文件链接，末尾加：**「批准后开始动手，有改动直接告诉我」**

### 模板 C：阶段三「完成」回复

直接说改了什么 + 验证结果 + 操作记录 md 链接，末尾加：**「已生成操作记录：doc/操作记录/xxxxx.md」**

### 模板 D：阶段三完成 → 提醒 commit（操作记录已生成后）

1. 引用本次操作记录文件链接
2. 贴生成的 commit message（见下方「四·五」模板）
3. 末尾加：**「你确认这个 commit message 我就提交；想改 wording 或增删改动点直接说」**

## 四、commit message 模板（提醒提交时使用）

> **适用场景：** 每次功能完成、操作记录生成后，提醒你提交 commit 用
> **原则：** 英文动词 + 中文描述，符合 Raycasting 项目习惯

```
feat(模块): 一句话描述（不超过 50 字）
- 关键改动点 1（文件：xxx.js）
- 关键改动点 2（文件：xxx.js）
- 关键改动点 3
```

> **动词规范：**
> - `feat` — 新功能（加武器、加门、加音效）
> - `fix` — 修复 bug（修正卡顿、修正 DDA 算法）
> - `refactor` — 代码重构（性能优化、拆模块）
> - `docs` — 文档改动（改工作流、加建议 md）
> - `chore` — 工具/配置（加 gitignore、改构建脚本）

## 五、操作记录的标准模板（按这个写，15-40 行）

> **适用场景：** 阶段三完成后，存档到 `doc/操作记录/`
> **长度目标：** 15-40 行，3 分钟内能读完
> **原则：** 有决策点的事详细写，纯操作的事简写，代码细节不抄（代码在源文件里）

```
# YYYY-MM-DD — <中文主题，不超过10字>

## 一、需求/问题

<用 2-5 行描述用户说了什么、或要解决什么问题。不用复述对话原文，概括即可。>

## 二、做了什么

<按要点列出，每条 1-2 行，不需要代码细节，源文件里随时能看。>

- <关键动作 1>，涉及文件：`xxx.js`
- <关键动作 2>，涉及文件：`xxx.js`
- ...

## 三、关键决策 / 踩过的坑（没有就写"无"，但通常至少有一点）

<为什么选这个方案而不是另一个？有没有临时绕过的问题？下次要注意什么？>
```
