## 二、对话基本流程（三阶段）

```
阶段一：理解与出大纲
  ├─ 助理理解用户问题
  ├─ 助理在 会话计划/ 下生成 "YYYY-MM-DD-<主题>-大纲.md"
  │   └─ 内容：问题理解 + 初步方向 + 待确认事项
  └─ 等待用户反馈（确认 / 修改 / 补充）
        ↓
阶段二：细化为执行计划
  ├─ 用户批准大纲后，助理在 会话计划/ 下生成 "YYYY-MM-DD-<主题>-执行计划.md"
  │   └─ 内容：步骤序号 + 每步目标 + 具体操作示例 + 先后依赖
  └─ 等待用户批准执行计划
        ↓
阶段三：执行 + 验证 + 记录
  ├─ 按执行计划逐步操作
  ├─ 执行 npm run build / lint / test 验证
  └─ 在 操作记录/ 下生成闭环文档 "YYYY-MM-DD-<主题>.md"
```

> **关键规则**：
> - 用户每次提问后，助理**必须先走阶段一**（除非是极其简单的一句话操作如"帮我改个错别字"）
> - 阶段二必须在**用户确认大纲后**才开始
> - 阶段三必须在**用户批准执行计划后**才开始
> - 三个阶段产生的三份文档（大纲、执行计划、操作记录）都要保留，方便事后回溯

## 二点五、自动记录规则（强制）—— 每次大型规划必须生成 md 文件

> **核心原则：只要在对话中产出了「大段的规划/方案/操作步骤/改进建议/架构设计/代码诊断」，必须立即生成 md 文件存档，不能只停留在对话消息里。**

### 什么算"大型规划"（必须存档）
以下内容出现时，**立即**在 `doc/_workflow/会话计划/` 或 `doc/` 下生成 md 文件：

| 内容类型 | 触发条件 | 存放位置 | 文件命名 |
|----------|----------|----------|----------|
| 改进建议/代码诊断 | 对项目做了深度代码阅读 + 问题诊断 + 改进方向（如"raycasting_改进建议.md"） | `doc/` 根目录 | `YYYY-MM-DD-<项目>-<主题>-建议.md` 或 `<主题>_建议.md` |
| 执行计划/分步操作 | 列出了 3 步以上的具体操作步骤、每步目标、涉及文件、验证方式 | `doc/_workflow/会话计划/` | `YYYY-MM-DD-<主题>-执行计划.md` |
| 大纲/初步方向 | 对用户需求做了理解复述 + 列出了初步方向（三阶段流程的阶段一产物） | `doc/_workflow/会话计划/` | `YYYY-MM-DD-<主题>-大纲.md` |
| 功能方案/架构设计 | 涉及"新建系统/模块架构/接口设计/数据结构重构"等大方案 | `doc/功能方案/<子目录>/` | `<主题>-方案.md` |
| 研究/调研报告 | 做了外部调研、技术选型比较、类似项目分析 | `doc/项目研究/` | `<主题>-研究.md` |

### 什么不算大型规划（可以不存档）
- 一句话回复（如"改了"、"跑通了"）
- 纯代码片段的即时反馈（如"这行改完了，你看看"）
- 对已有 md 文件的小范围修改意见

### 生成时机
1. **在对话回复用户之前**，先生成 md 文件
2. 生成后在回复中**明确告知用户**文件已存档的位置
3. 回复内容本身可以保留大段文字，但 md 文件要有更结构化、更完整的版本

### 一个反例（避免发生）
> ❌ 错误做法：在对话中写了一份 6 步的详细重构计划，但没有存为 md 文件，事后无法在 `doc/` 目录下找到这份计划。
>
> ✅ 正确做法：先写 md 文件保存完整计划 → 再在对话中回复（可贴关键段落），并告知文件位置。

## 三、doc 文档管理规范

### 3.1 文件存放规则

```
doc/
├── _workflow/                         ← 工作流核心（永远不要删除）
│   ├── 对话工作流.md                  ← 本文件（规则说明）
│   ├── todoList.md                    ← 大任务清单
│   └── 会话计划/                      ← 每次对话的大纲 + 执行计划（历史档案）
│       └── YYYY-MM-DD-<主题>-大纲.md
│       └── YYYY-MM-DD-<主题>-执行计划.md
├── 操作记录/                          ← 代码改动的闭环记录（每改一次存档一次）
│   └── YYYY-MM-DD-<主题>.md
├── 项目研究/                          ← 项目分析、代码诊断、调研报告
│   └── <主题>-研究.md / <主题>-诊断.md
├── 功能方案/                          ← 功能模块的方案设计（如"AI对话功能改造/"）
│   └── <子目录>/<方案>.md
└── <项目根目录内的其他临时建议文件>    ← 例如 raycasting_改进建议.md（放在项目 doc 根目录方便快速找到）
    └── <主题>_建议.md / <项目>-改进建议.md
```

### 3.2 命名规范

| 文件类型 | 命名规则 | 示例 |
|----------|----------|------|
| 建议/诊断类 | `<项目>-<主题>-建议.md` 或 `<主题>_建议.md` | `raycasting_改进建议.md` |
| 大纲 | `YYYY-MM-DD-<主题>-大纲.md` | `2026-06-14-raycasting重构-大纲.md` |
| 执行计划 | `YYYY-MM-DD-<主题>-执行计划.md` | `2026-06-14-raycasting重构-执行计划.md` |
| 操作记录 | `YYYY-MM-DD-<主题>.md` | `2026-06-14-raycastingDDA重构.md` |
| 研究/调研 | `<主题>-研究.md` | `光线投射引擎-DDA算法-研究.md` |

规则：
- 主题词用**中文**，不超过 **10 个字**
- 日期用 **YYYY-MM-DD** 格式
- 同一主题的多个版本用 `-v2`、`-v3` 区分，不要覆盖旧版本

### 3.3 文件生命周期与清理

| 阶段 | 文件位置 | 是否保留 | 说明 |
|------|----------|----------|------|
| 对话进行中 | `会话计划/`（大纲 + 执行计划） | ✅ 保留 | 作为本次对话的决策记录 |
| 代码执行完成 | `操作记录/` | ✅ 保留 | 闭环记录，包含改动文件清单和验证结果 |
| 项目研究/诊断 | `项目研究/` | ✅ 永久保留 | 方便后续了解项目历史 |
| 功能方案 | `功能方案/<子目录>/` | ✅ 永久保留 | 作为设计档案 |
| 临时建议/草稿 | `doc/` 根目录（如 `raycasting_改进建议.md`） | ✅ 保留至项目结束 | 这些是核心决策输入，项目完成后归档 |

**清理规则：永远不要主动删除任何 doc 下的 md 文件**。文件过多时的管理方式：
- 用**目录**归类，不要删除
- 同一主题的多版文件保留在同一目录下（如 `raycasting/` 子目录）
- 如果确实要整理，先向用户确认

### 3.4 如何快速查找（助理的检查顺序）

每次开新对话时，助理按以下顺序检查文档：

1. `doc/_workflow/todoList.md` → 了解当前有什么大任务
2. `doc/_workflow/会话计划/` → 倒序查看最近 2-3 份执行计划，了解进度
3. `doc/操作记录/` → 倒序查看最近 2-3 份操作记录，了解最近改了什么
4. `doc/项目研究/` → 如果涉及架构/算法问题，看有没有现成研究
5. `doc/` 根目录 → 看有没有 `<项目>-建议.md` 类文件

## 四、TodoList 维护规范

**文件位置**：`doc/_workflow/todoList.md`

**格式**：

```
# todoList

## 进行中 (In Progress)
- [ ] 任务描述（YYYY-MM-DD 开始）

## 待处理 (Backlog)
- [ ] 任务描述

## 已完成 (Done)
- [x] 任务描述（YYYY-MM-DD 完成）
```

**规则**：
- 粒度为**大任务级别**（如"优化 AI 聊天组件"），不是细分步骤

- 开始执行 → 移到"进行中"并标注开始日期
- 完成后 → 移到"已完成"并标注完成日期

## 八、回复风格

- **更主动**：主动发现代码中的问题、主动提出改进建议
- 发现明显 bug 或潜在问题时直接指出，不等待用户问
- 有更好的实现方案时，主动提出并说明原因
- 阶段一的大纲回复：**直接贴 md 文件内容 + 文件链接**，让用户方便看也方便找
- 阶段二的执行计划回复：**直接贴 md 文件内容 + 文件链接**，附上"批准就开工"的提示
- **自动记录硬性要求**：只要在对话中产出了 3 步以上的操作计划、或任何形式的大段方案建议，回复用户前**必须先生成 md 文件**，然后在回复末尾明确告知：`已生成文档：doc/xxx/xxxxx.md`

---

## 九、代码改动基本原则

1. **改动前先读**：先查看相关文件，理解现有代码风格
2. **改动后验证**：执行 `npm run build` 确认无编译错误
3. **不引入新依赖**：除非用户明确同意，否则避免新增 package.json 依赖
4. **不添加无意义注释**：保持代码本身的可读性
5. **遵循现有风格**：与项目已有代码保持一致

## 十、项目范围界定

本工作目录包含两类内容，处理方式不同：

| 类型 | 位置 | 处理方式 |
|------|------|---------|
| 代码开发 | `app/src/` 下的 React 项目 | 大纲 → 执行计划 → 实现 → 验证 → 记录 |
| 内容/研究 | 根目录 `research/`、`doc/个人资料/resume/` 文档 | 理解目标 → 生成/整理内容 → 记录 |

## 十一、什么时候可以跳过阶段一和阶段二

以下情况可以**直接执行，不生成大纲和执行计划**：

1. **一句话操作**：如"帮我改个错别字"、"帮我跑一下 npm run build"、"帮我看看某个文件"
2. **纯信息查询**：如"xxx 是什么"、"xxx 怎么用"、"项目里有没有 xxx"
3. **已有明确且极简单的执行计划**：如"把 xxx 文件里的 A 改成 B"

判断标准：如果助理在回复前**不需要先做探索（搜索/读文件）**，可以直接操作 → 跳过大纲和执行计划。否则必须走三阶段流程。
