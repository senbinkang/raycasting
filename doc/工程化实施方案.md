# Raycasting 项目工程化实施方案（v4）

## 一、项目现状分析

### 1.1 当前技术栈
- **语言**：纯 JavaScript（ES5/ES6）
- **渲染**：HTML5 Canvas API
- **运行方式**：直接打开 `raycasting.html`，通过 `<script>` 标签按顺序加载
- **依赖管理**：无（纯原生实现）

### 1.2 当前项目结构
```
raycasting/
├── raycasting.html          # 入口 HTML（内联 CSS + 脚本引用）
├── index.js                 # 主程序入口（仅 10 行）
├── utils.js                 # 工具函数（Vec, Color, draw* 等）
├── Player.js                # 玩家控制
├── Background.js            # 地图数据与小地图绘制
├── textures.js              # 程序化纹理生成
├── game/                    # 游戏模块
│   ├── Game.js              # 游戏主循环
│   ├── GameScene.js         # 场景管理器
│   ├── Screen.js            # 3D 视图核心算法
│   ├── Sprite.js            # 精灵基类
│   ├── SpriteManager.js     # 精灵管理
│   ├── Weapon.js            # 武器系统
│   ├── AudioManager.js      # 音效管理
│   ├── CommentaryService.js # AI 解说服务
│   ├── CommentaryAudioCache.js
│   ├── CommentaryVoiceSample.js
│   └── OverlayScreen.js     # 覆盖层画面
├── assets/
│   └── yuqian_voice_sample.wav
└── scripts/
    └── generate_audio_cache.mjs
```

### 1.3 存在的问题

| 问题类别 | 具体问题 | 影响 |
|---------|---------|------|
| **项目结构** | 模块散落在根目录，无清晰分层 | 难以维护和扩展 |
| **依赖管理** | 无 package.json，通过 script 标签手动管理依赖顺序 | 容易遗漏或顺序错误 |
| **构建流程** | 无构建工具，无法进行代码压缩、Tree Shaking | 生产环境包体积大，加载慢 |
| **代码规范** | 无 ESLint/Prettier，代码风格不统一 | 团队协作困难，易产生 Bug |
| **类型安全** | 纯 JS，无类型检查 | 运行时错误难以发现 |
| **测试** | 无测试框架，全手动测试 | 回归测试成本高，易引入回归 Bug |
| **CI/CD** | 无自动化流程 | 部署依赖人工操作，易出错 |
| **模块化** | 使用全局变量，无模块化封装 | 命名冲突风险，难以复用 |

## 二、工程化改造方案

### 2.1 技术选型

| 领域 | 工具/技术 | 版本 | 选型理由 |
|------|----------|------|---------|
| **构建工具** | Vite | ^6.5.0 | 极速开发体验，原生 ES Module 支持，Rollup 生产构建 |
| **语言** | JavaScript (ES Module) | ES2022+ | 渐进式改造，降低迁移成本 |
| **代码规范** | ESLint | ^9.0.0 | 业界标准，规则丰富，自动修复 |
| **代码格式化** | Prettier | ^3.2.0 | 统一代码风格，减少格式化争议 |
| **测试框架** | Vitest | ^2.0.0 | 与 Vite 深度集成，极速测试运行 |
| **断言库** | Vitest 内置 | - | 无需额外依赖 |
| **覆盖率** | Vitest + c8 | - | 原生支持，配置简单 |
| **Git Hooks** | Husky | ^9.0.0 | 轻量级 Git Hooks 管理 |
| **提交规范** | Commitlint | ^19.0.0 | 统一提交信息格式 |
| **包管理** | npm | ^10.0.0 | 稳定可靠，与 Vite 配合良好 |

### 2.4 代码规范与质量控制

#### 2.4.1 ESLint 规则配置

**核心规则**：
- `no-unused-vars`：禁止未使用变量
- `no-undef`：禁止未定义变量（需配置 globals）
- `prefer-const`：优先使用 const
- `arrow-parens`：箭头函数参数括号规范
- `curly`：强制花括号
- `eqeqeq`：强制全等比较
- `no-console`：生产环境禁止 console

**环境配置**：
- browser：启用浏览器全局变量（window, document, console）
- es2022：启用 ES2022 语法支持

#### 2.4.2 Prettier 配置

```json
{
  "semi": false,
  "singleQuote": true,
  "trailingComma": "es5",
  "printWidth": 120,
  "tabWidth": 4
}
```

#### 2.4.3 Git Hooks

**pre-commit**：
```bash
npx lint-staged
```

**lint-staged 配置**：
```json
{
  "*.{js,jsx}": ["eslint --fix", "prettier --write"],
  "*.{css,html}": ["prettier --write"]
}
```

**commit-msg**：
```bash
npx --no -- commitlint --edit $1
```

### 2.7 CI/CD 流程设计

#### 2.7.1 CI 流程（GitHub Actions）

**触发条件**：
- push 到任何分支
- pull_request 到 main 分支

**流程步骤**：
1. **Checkout**：拉取代码
2. **Setup Node.js**：安装 Node.js 20
3. **Install Dependencies**：`npm ci`
4. **Lint**：`npm run lint`
5. **Test**：`npm run test:coverage`
6. **Build**：`npm run build`

#### 2.7.2 CD 流程

**触发条件**：
- push 到 main 分支（或创建 release）

**流程步骤**：
1. 执行 CI 流程（同上）
2. **Deploy**：将 `dist/` 目录部署到 GitHub Pages

#### 2.7.3 分支策略

```
main          # 稳定版本（自动部署）
├── v4-*      # 功能开发分支
└── hotfix-*  # 紧急修复分支
```

## 五、实施过程中的注意事项

### 5.1 兼容性注意事项

| 问题 | 解决方案 |
|------|---------|
| 全局变量依赖 | 使用 ES Module 导出/导入，逐步消除全局变量 |
| Canvas API 兼容性 | 保持现有实现，Vite 会自动处理 polyfill |
| Audio API 兼容性 | 保持现有实现，添加浏览器兼容性检测 |

### 5.2 迁移风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 模块引用错误 | 游戏无法运行 | 逐步迁移，每次迁移后验证 |
| 构建配置错误 | 无法构建 | 参考 Vite 官方文档，使用最小配置 |
| 测试覆盖率低 | 无法及时发现回归 Bug | 优先编写核心模块测试 |
| Git Hooks 冲突 | 提交被拒绝 | 配置合理的规则，提供自动修复 |

### 5.3 性能注意事项

| 问题 | 解决方案 |
|------|---------|
| Vite 开发服务器性能 | 确保只在需要时热更新 |
| 生产构建体积 | 启用 Tree Shaking，压缩代码 |
| 测试运行速度 | 并行运行测试，使用 Vitest 的快速模式 |

### 5.4 团队协作注意事项

- 所有成员需安装相同版本的工具链（通过 package-lock.json 保证）
- 提交信息需遵循 Conventional Commits 规范
- 代码审查时需关注 lint 和测试结果
- 定期同步依赖更新情况

### 6.2 Conventional Commits 规范

```
<type>(<scope>): <description>

<optional body>

<optional footer>
```

**常用 type**：
- `feat`：新功能
- `fix`：修复 Bug
- `refactor`：代码重构
- `docs`：文档更新
- `test`：测试代码
- `chore`：构建/工具相关
- `style`：代码格式（不影响功能）

### 6.3 代码提交示例

```bash
# 新功能
git commit -m "feat(engine): 添加碰撞检测优化"

# 修复 Bug
git commit -m "fix(game): 修复敌人不攻击的问题"

# 重构
git commit -m "refactor(audio): 重构音频管理器"

# 测试
git commit -m "test(utils): 添加 Vec 类测试用例"
```
